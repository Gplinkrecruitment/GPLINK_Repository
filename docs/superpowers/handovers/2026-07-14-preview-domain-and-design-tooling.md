## 3. ⚠️ UNFIXED BUG — the marketing site is indexable on every host

**Most important open item. Must be fixed BEFORE the www cutover.**

### The problem

`/robots.txt` is **generated by the app**, identically, on **every host it answers on** (`server.js` ~line 58240):

```js
if (pathname === '/robots.txt') {
  const body = `User-agent: *\nAllow: /\nSitemap: ${PUBLIC_BASE_URL}/sitemap.xml\n`;
```

Verified live — both return `Allow: /`:
- `https://app.mygplink.com.au/robots.txt`
- `http://preview.mygplink.com.au/robots.txt`

And `https://app.mygplink.com.au/jobs` returns **200** — marketing sub-routes still resolve on the app host (commit `7c2593a` explicitly left them there "for now").

### Why it matters

After the cutover there will be **three live, word-for-word identical copies** of the marketing site, all telling Google "index me":

1. the real site (apex or www)
2. `preview.mygplink.com.au`
3. `app.mygplink.com.au/jobs`, `/about`, `/faq`, …

Google picks the canonical itself and doesn't always pick right — `preview.mygplink.com.au` can surface in search results instead of the real site, and duplicates dilute ranking. **The cutover does not fix this; it's the moment it starts to bite.**

### The fix (not yet written)

Make the app host-aware:
- **Canonical marketing host** → `robots.txt` = `Allow: /` (as today).
- **Every other host** (`preview.*`, `app.*`, `admin.*`, `*.vercel.app`) → send an `X-Robots-Tag: noindex` response header, and reflect that in `robots.txt`.
- Drive it off a `MARKETING_CANONICAL_HOSTS` constant/env so it's a one-line flip. Treat **both** apex and www as canonical (one 301-redirecting to the other) so it's correct whichever the owner picks.

⚠️ **Do NOT rely on `robots.txt: Disallow` alone for the non-canonical hosts.** Disallow stops Google *crawling*, which means it can never *see* a `noindex` — and a disallowed URL can still be indexed if something links to it. The `X-Robots-Tag` header is the reliable mechanism; allow the crawl so the header is seen.
